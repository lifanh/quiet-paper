# quiet-paper design-sync notes

## Known render warns (accepted, don't chase on re-sync)

- **`[FONT_MISSING]` — "Iowan Old Style", "Palatino Linotype", "Palatino"**: these
  are OS-native serif fonts referenced in `--font-sans`
  (`"Iowan Old Style", "Palatino Linotype", Palatino, Georgia, serif`), not
  brand fonts shipped anywhere in this repo — the stack already ends in a
  generic `serif` fallback by design. Accepted 2026-07-24 with the user's
  explicit OK ("Accept system fonts for now. I'll add custom fonts later.").
  No `cfg.extraFonts`/`cfg.runtimeFontPrefixes` set. **Re-sync risk**: if a
  real brand font is added later, this line should be revisited — it will
  keep silencing `[FONT_MISSING]` for any newly-added family too, since the
  check is unconditional acceptance, not scoped to these three names.

## Build / CSS generation (re-sync risk — read before re-syncing)

quiet-paper ships **no compiled CSS** in `dist/` — Tailwind v4 utility classes
are generated by the *consuming app's own* Tailwind build from
`styles/tokens.css` + `styles/tailwind-theme.css` (`@theme` bridge) +
`styles/tailwind-sources.css` (`@source "../dist"` for class detection).
This is "Pattern A" per `docs/ARCHITECTURE.md`.

To get a real, usable `cfg.cssEntry` for design-sync, we compile our own
stylesheet using an isolated Tailwind CLI (matching the repo's own installed
`tailwindcss@4.3.2`, found in the main `node_modules/` as a transitive dep of
`@tailwindcss/typography`):

- `.ds-sync/tailwind-entry.css` — `@import "tailwindcss"; @plugin "@tailwindcss/typography"; @import "../styles/tailwind-sources.css"; @import "../styles/tokens.css" layer(theme); @import "../styles/tailwind-theme.css"; @import "../styles/prose.css";`
- `.ds-sync/node_modules/.bin/tailwindcss -i .ds-sync/tailwind-entry.css -o .ds-sync/tailwind-out/compiled.css` (installed via `@tailwindcss/cli@4.3.2` in the isolated `.ds-sync` deps, pinned to match the repo's own tailwindcss version)
- `cfg.buildCmd` runs `npm run build` (vite, produces `dist/`) then this compile step
- `cfg.cssEntry` points at `.ds-sync/tailwind-out/compiled.css`

**`styles/prose.css` (added 2026-07-26)**: as of the token-layer refactor
(`docs/ARCHITECTURE.md` "Containing Tailwind's `--tw-*` internals"), `Prose`
no longer authors `--tw-prose-*` via arbitrary-value utility classes —
they're declared once under `.qp-prose` in `styles/prose.css`, applied by the
component itself. `tailwind-entry.css` must `@import` this file too, or the
compiled bundle CSS is missing the `.qp-prose` rule and the `Prose` preview
renders with Tailwind Typography's default (unthemed) colors instead of
quiet-paper's. Verified after the fix: `Prose`'s `_ds_sync.json` render hash
is unchanged from before the refactor — the source change is a pure
refactor, confirmed pixel-equivalent by the sync's own render hash, not just
asserted.

**Re-sync risk**: if the repo's `tailwindcss` version (currently resolved via
`@tailwindcss/typography`'s peer dep) changes, re-check `.ds-sync`'s installed
`@tailwindcss/cli` version still matches — a mismatch won't error, it'll just
compile against a different Tailwind engine than what the DS actually ships
with. Also: if a new component/page introduces new utility classes not yet
used anywhere the `@source "../dist"` scrape sees, they won't appear in the
compiled stylesheet until `npm run build` regenerates `dist/` with that usage
baked in (this is inherent to Tailwind's content-scanning model, not
specific to this sync). And: if quiet-paper ever adds a *second* plain CSS
file with component-scoped variable overrides (the same pattern as
`prose.css`), `tailwind-entry.css` needs a matching `@import` line or its
rules silently never reach the compiled bundle — this isn't auto-discovered,
it's hand-wired per file.

## Forked lib scripts (`.design-sync/overrides/`)

`quiet-paper`'s `package.json` declares TypeScript types only under
`exports["."].types` (a valid modern exports-only shape, no legacy top-level
`types`/`typings` field). Two converter modules needed forking to handle it —
no `cfg.*` field covers this heuristic:

- **`dts.mjs`**: `projectFor()`'s entry-file resolution fell back to a
  hardcoded, nonexistent `<pkgDir>/index.d.ts` when `pkgJson.types`/`typings`
  were absent, so the ts-morph project's entry source file was never added
  and `exportedNames()`/`loadDts()` silently returned zero exports (the
  build logged `[ZERO_MATCH] ... treating as tokens-only DS` and dropped all
  9 components with no error). Fork adds an `exports["."].types` (or
  `exports["."].<condition>.types`) lookup ahead of that fallback.
- **`source-kit.mjs`**: has its own hardcoded `import ... from './dts.mjs'`
  — a sibling import that bypasses `package-build.mjs`'s `loadLib()`
  override registry (that registry only intercepts the top-level modules
  `package-build.mjs` imports directly). Forking `dts.mjs` alone was
  insufficient because `source-kit.mjs`'s component discovery still ran the
  *original* `dts.mjs`. Forked so its local `./dts.mjs` import resolves to
  the patched sibling in the same `overrides/` dir; its other relative
  imports (`common.mjs`, `bundle.mjs`) are repointed at `../../.ds-sync/lib/`
  since no siblings exist for them in `overrides/`.

**Re-sync risk**: if `@lifanh/quiet-paper` ever adds a top-level `types` (or
`typings`) field to `package.json`, both forks become unnecessary (the
bundled `dts.mjs` would resolve the entry correctly on its own) — safe to
delete `.design-sync/overrides/{dts,source-kit}.mjs` and the corresponding
`cfg.libOverrides` entries at that point, then do a full rebuild + re-verify
(fork removal moves the grade contract per the design-sync skill's own
note). If bundled `lib/dts.mjs` or `lib/source-kit.mjs` change upstream in a
future design-sync skill version, diff them against these forks and
re-apply the same two patches.

**Fresh clone / new machine setup**: recreate the fork resolution symlink
(gitignored, not committed) before re-running the converter:
```
ln -sfn ../.ds-sync/node_modules .design-sync/node_modules
```
